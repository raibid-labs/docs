  | Component     | Technology        | Purpose
           |
  |---------------|-------------------|-------------------------------------
  ---------|
  | Static Site   | Hugo              | Fast builds, Go templates
           |
  | Styling       | Tailwind CSS      | Utility-first CSS

  Key insight: Vector keeps rustdoc separate from their main docs site. They

  rustdoc's output format is opinionated.

  Downside for you: This stack requires Node.js, Go, and significant
  frontend expertise. It's overkill for a small org where you're the primary
   maintainer.

  ---
  Part 2: Push vs Pull Model Analysis

  Current Setup (Pull Model)

  raibid-labs/docs ──pulls from──> repo-1/docs
                                   repo-2/docs
                                   repo-n/docs

  Pros: Centralized control, single build pipeline
  Cons: Stale if repos forget to trigger sync, complex submodule management

  Alternative: Push Model

  repo-1 ──pushes docs to──> raibid-labs/docs (or S3/separate hosting)
  repo-2 ──pushes docs to──>
  repo-n ──pushes docs to──>

  Pros: Docs update when code updates, each repo owns its pipeline
  Cons: Requires CI/CD in every repo, aggregation becomes "assembly" not
  "generation"

  Hybrid Model (Recommended)

  Per-repo: Generate + host own polished docs (rustdoc + mdbook)
  Central:  Pull raw markdown only for Obsidian aggregation

  This separates concerns:
  - Per-repo: Beautiful branded documentation site
  - Central: Knowledge aggregation for YOUR consumption (Obsidian)

  Part 3: Recommended Architecture

  Layer 1: Per-Repository Documentation (Push Model)

  Each Rust project should have:

  repo/
  ├── src/           # Rust code with /// doc comments
  ├── docs/          # AI-generated + prose markdown (Obsidian-compatible)
  │   ├── .obsidian/       # Obsidian vault config + plugins
  │   ├── index.md
  │   └── ...
  ├── book/          # mdBook source for tutorials/guides (optional)
  │   ├── book.toml
  │   └── src/
  └── .github/workflows/
      └── docs.yml   # Generates: rustdoc + mdbook + publishes

  CI/CD per repo (docs.yml):
  1. cargo doc --workspace --no-deps → rustdoc output
  2. mdbook build (if book/ exists) → tutorial site
  3. Deploy to GitHub Pages at raibid-labs.github.io/repo-name/
  4. (Optional) Trigger central aggregator via repository_dispatch

  Why this works: Each repo becomes self-contained. Clone it, open docs/ in
  Obsidian, and you have a working vault. The public site is auto-generated.

  Layer 2: Central Obsidian Aggregator (Pull Model)

  Keep your current raibid-labs/docs but simplify its purpose:

  raibid-labs/docs/
  ├── content/
  │   ├── projects/        # Submodules pointing to each repo's docs/
  │   │   ├── project-1 → raibid-labs/project-1/docs
  │   │   └── ...
  │   └── meta/            # Cross-project notes, architecture decisions
  ├── .obsidian/           # Central vault config
  └── scripts/             # Nushell aggregation (keep this)

  Key change: This repo is primarily YOUR Obsidian notebook. Public-facing
  polished docs live in each individual repo. This aggregator can still be
  published via Quartz, but its primary audience is you.

  Layer 3: Meta-Org Hub (Optional, Future)

  If you want to aggregate across multiple orgs (raibid-labs, fusabi-lang,

  - Use VSCode + Foam when coding

  - https://github.com/Vinzent03/obsidian-git handles sync

  My recommendation: Start with Foam. If you find yourself wanting more,

  You mentioned this. Here's what it would need:
  - Markdown preview with wikilink support

  - Quick switcher for [[links]]

  requirements Foam doesn't meet, I'd avoid this rabbit hole.

        - name: Deploy to GitHub Pages

  The challenge is that rustdoc generates HTML, not markdown, so it doesn't
  fit natively into Quartz's markdown pipeline. But there are several ways
  to include it:

  Option 1: Subpath Hosting (Simplest)

  Each repo pushes its rustdoc HTML to the central docs repo:

  raibid-labs/docs/
  ├── content/           # Markdown → Quartz processes this
  │   └── projects/
  ├── public/            # Static assets Quartz copies as-is
  │   └── api/
  │       ├── project-1/ # rustdoc HTML from repo 1
  │       ├── project-2/ # rustdoc HTML from repo 2
  │       └── ...

  Quartz (and most static site generators) can serve pre-built HTML at
  subpaths. Your markdown docs link to /api/project-1/ for API references.

  Push workflow: Each repo's CI builds rustdoc → pushes to
  raibid-labs/docs/public/api/{repo-name}/

  Option 2: Unified Workspace Crate

  Create a "docs-only" crate that depends on all your published crates:

  # raibid-labs/docs/api-docs/Cargo.toml
  [package]
  name = "raibid-api-docs"
  version = "0.0.0"
  publish = false

  [dependencies]
  project-1 = { git = "https://github.com/raibid-labs/project-1" }
  project-2 = { git = "https://github.com/raibid-labs/project-2" }
  # or from crates.io if published

  Then cargo doc --no-deps generates unified, cross-linked API docs for
  everything. This is how Tokio and other large ecosystems do it.

  Option 3: Convert to Markdown

  Tools like https://crates.io/crates/cargo-readme or custom scripts can 
  extract doc comments into markdown:

  cargo readme -i src/lib.rs > docs/api/project-1.md

  This loses rustdoc's interactivity but integrates cleanly into Quartz. You
   could generate both—markdown summary for the knowledge base, full rustdoc
   HTML at a subpath.

  Option 4: Different Static Site Generator

  If Quartz feels limiting, alternatives that handle mixed content better:

  | Tool                   | Pros                                    | Cons
                         |
  |------------------------|-----------------------------------------|------
  -----------------------|
  | mdBook                 | Rust-native, can embed rustdoc          | Less
  pretty than Quartz     |
  | Docusaurus             | Plugin ecosystem, rustdocusaurus exists |
  Node.js, heavier            |
  | Hugo (Vector's choice) | Fast, flexible, subpath hosting easy    | Go
  templates, steeper curve |
  | Zola                   | Rust-native, fast                       |
  Smaller ecosystem           |

● What is "subpath"?

  Just a URL path segment. If your site lives at
  raibid-labs.github.io/docs/:

  raibid-labs.github.io/docs/           ← root (Quartz markdown)
  raibid-labs.github.io/docs/api/       ← subpath (rustdoc HTML)
  raibid-labs.github.io/docs/api/crate-a/
  raibid-labs.github.io/docs/api/crate-b/

  The static site generator serves different content at different paths.
  Quartz processes markdown at root, but passes through pre-built HTML in
  public/api/ unchanged.

  Honest Assessment

  VSCode Extension: There's a real opportunity, but it's narrow:

  1. "Rust Knowledge Bridge" - A VSCode extension that:
    - Indexes your rustdoc output
    - Lets you [[link-to-api:crate::module::Function]] in markdown
    - Shows "related notes" in the Rust code hover
    - Generates markdown stubs from rustdoc

  This would be genuinely useful for Rust developers who document heavily.
  Foam doesn't understand Rust; this would add that layer.

  Effort: Medium-high (need to parse rustdoc JSON output, integrate with

  Benefit: Real, but niche audience

  Obsidian Extension: Less opportunity IMO because:
  - Obsidian already has a rich plugin ecosystem
  - You can't write code in Obsidian anyway, so the bridge problem remains
  - The https://github.com/pjeby/obsidian-rust-plugin idea has been explored

  Are You Building Another Static Site Generator?

  Short answer: No, but you might be building a documentation orchestration 
  system.

  The distinction:
  - Static site generator: Takes input files → outputs HTML (Hugo, Quartz,
  Docusaurus)
  - Documentation orchestration: Coordinates multiple generators +
  aggregates + themes + deploys

  You don't need to build the generators. They exist:
  - rustdoc, pydoc, godoc, TypeDoc (API reference)
  - mdBook, Docusaurus, MkDocs, Quartz (prose docs)

  What's missing is the glue:
  - Combine outputs from multiple generators
  - Apply consistent theming
  - Aggregate across repos
  - Keep Obsidian-compatible source files

  This glue is what you'd be building.

  Dinodoc (Closest to What You Want)

  https://github.com/dundalek/dinodoc is a polyglot documentation system
